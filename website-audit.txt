KENORATECH OS — SOURCE CODE AUDIT & TECHNICAL DOCUMENTATION
Audit scope: current workspace source, configuration templates, docs, and tests
Audit date: 2026-11-07

SCOPE AND METHOD
----------------
This report describes the implementation present in this workspace. Source,
configuration templates, route definitions, model declarations, UI modules,
provider service code, scripts, and the existing test file were inspected. The
local server/.env and client/.env were not opened; live database records and
provider accounts were not accessed. No database operation, seed script,
migration, test suite, install, or cleanup operation was run for this audit.
The preceding implementation work ran TypeScript checking and production
builds successfully. Provider API calls were not verified against live
accounts. The only automated tests found are two API access tests; the suite
was not run as part of this audit.

Status labels used below:
- Implemented: source contains the described behavior.
- Verified: an automated check or directly inspectable behavior provides
  evidence; this does not imply a live production deployment was inspected.
- Partial: a working subset exists, with notable scope still missing.
- Placeholder: UI/configuration exists, but the advertised operation is not
  implemented.
- Not implemented: no corresponding implementation was found.
- Potentially broken: source shows a concrete condition that can fail.

SECTION 1 — PROJECT OVERVIEW
----------------------------
KenoraTech OS is a private, single-administrator project and operations
workspace. It is intended for the owner/admin managing a portfolio of software
projects. It is not currently a multi-user project-management SaaS: there is
one admin role, no public signup, no invitations, and no per-user workspace
permissions.

Implemented capability areas:
- Admin login and MongoDB-backed sessions.
- Project portfolio, editable status and metrics, archive/restore/duplicate,
  text search, status filtering, and project details.
- Tasks, a status-column Kanban presentation, milestones, folders, categories,
  and technology catalogues.
- Generic records for clients, leads, services, proposals, invoices, finance,
  security, technical debt, testing, deployment metadata, infrastructure,
  documents metadata, notifications, and backup metadata.
- Private document upload/download/replacement with embedded version metadata.
- MongoDB metadata export/import and additive snapshot backup/restore.
- Dashboard aggregates and local activity records.
- Read-only recent activity fetches from GitHub, Vercel, and Render
  Pages/Workers where credentials and matching project resource information
  are configured.

Architecture:
- `client/`: React single-page application, React Router, TanStack Query,
  Vite, TypeScript, and CSS.
- `server/`: Express API, Mongoose models, session middleware, Zod request
  parsing, provider fetch service, and file upload routes.
- MongoDB stores operational records and connect-mongo stores sessions.
- Browser requests target `/api/v1` through `client/src/services/api.ts`.
- The API is a separate Node service; it does not serve the Vite client.

Versions declared in package manifests:
- Node requirement in README/guide: Node.js 20 or newer. Runtime version is
  not pinned by a version file found in the inspected tree.
- React 19.2.0, React DOM 19.2.0, Vite 7.1.12, TypeScript 5.9.3,
  React Router DOM 7.9.4, TanStack Query 5.90.2, Recharts 3.3.0.
- Express 5.1.0, Mongoose 8.19.1, Zod 4.1.12, express-session 1.18.2,
  connect-mongo 5.1.0, bcrypt 6.0.0, Helmet 8.1.0, Multer 2.0.2.
- Exact transitive package versions are governed by `package-lock.json`; the
  lockfile was not expanded into this report.

Deployment architecture documented in `guide.txt` and `docs/deployment.md`:
Vercel static client, Render Node API, and MongoDB Atlas database. This is an
intended setup, not evidence that any production deployment currently exists.

SECTION 3 — FEATURE INVENTORY
-----------------------------

1. Authentication and admin access — PARTIAL / IMPLEMENTED
Frontend: Login and shell in `client/src/app/App.tsx`.
Backend: `/auth/login`, `/auth/logout`, `/auth/me`; `requireAuth` middleware.
Database: `User`; session collection via connect-mongo.
Workflow: seeded admin submits email/password; bcrypt compare; session ID is
regenerated; HttpOnly cookie holds session ID; browser queries `/auth/me`.
Validation: email and bounded password lengths through Zod; login rate limit.
Logout destroys session and clears cookie. Errors are JSON and UI errors shown.
Limits: no password reset/change UI, MFA, recovery, account administration, or
public registration. Seed script will not rotate a pre-existing password.
Role is stored but all authenticated routes share the same `requireAuth` check;
there is no separate role authorization check. Functional login was not tested
against live DB credentials during this audit.

2. Main dashboard — IMPLEMENTED; live provider status not verified
Frontend: `Dashboard.tsx`; API `GET /dashboard`.
Database: Project, ActivityLog, Milestone, Task.
Shows project status counts/chart, active/development totals, critical-risk
count, upcoming milestone count, overdue task count, average recorded project
health score, estimated/actual/revenue values on project records, recent
projects and recent activity. Refresh refetches. New Project navigates to
project list rather than directly opening the create dialog.
Integrations tile reports credential configuration, not a verified connection.
Dashboard calculations are based on explicitly stored project fields; Finance
WorkspaceRecord entries are not included in the three project financial sums.
The dashboard/API does not fabricate missing data.

3. Analytics and reports — PARTIAL
Frontend: `AnalyticsPage` in `SystemPages.tsx`; routes `/analytics`, `/reports`.
API: `/dashboard`, `/projects?limit=100`, `/records/finance`.
Shows aggregate cards and project rows; CSV contains project/status/priority/
updated/health fields for the fetched page and can be downloaded.
Not a full time-series/revenue analysis; project list is capped at 100 by UI
request and does not iterate all pages for CSV. Analytics loading handles
loading; an error view is present. Report is substantially the same view.

4. Project management — IMPLEMENTED, with relationship gaps
Frontend: `Projects.tsx`, `ProjectDetails.tsx`.
API: GET/POST/PATCH/DELETE `/projects`, detail GET, and archive/restore/
duplicate actions. Model `Project`.
Create/edit fields include name, description, status, priority, risk, progress,
health, financial values and resource URLs. Listing has status filter, text
search, page controls (100 rows per request), archive, restore, duplicate,
delete. Details include overview, tasks, milestones, technology, GitHub,
deployments, documents, security, debt, testing, finance, activity, settings.
Validation: Zod and Mongoose enum/range/length checks; slug uniqueness.
Delete blocks associated tasks, milestones and generic records referencing the
project, but does not check documents or all possible loose relationships.
Archiving preserves records. Duplicate starts as planning/unassessed but
copies other source properties and provider resource references unless fields
are explicitly reset; provider links may therefore point at the same resources
after duplication. The detail-page “Deployments” tab takes the provider feed
branch, so generic deployment records loaded for that tab are not displayed.

5. Tasks and Kanban — IMPLEMENTED; Kanban interaction is limited
Frontend `Tasks.tsx`; `TasksPage` in `RecordPage.tsx`? The active implementation
is `client/src/features/workspace/Tasks.tsx`; an older duplicate-looking
TasksPage export also exists in `Collections.tsx` and is not used by App.
API GET/POST/PATCH/DELETE `/tasks`; model `Task` and optional Project/Milestone
references. Create task supports title, optional project and date; task status
can be changed through select/checkbox; delete available. Kanban is columns by
status with dropdown status changes, not drag-and-drop. Backend supports more
fields than frontend exposes. Dashboard overdue count excludes Done tasks.
Task changes do not consistently create ActivityLog rows.

6. Milestones and roadmap — IMPLEMENTED, partial UI
Frontend `Milestones.tsx`; `/milestones` and `/roadmap` route to same page.
API GET/POST/PATCH/DELETE `/milestones`; model requires Project, allows due date,
status and dependency ObjectIds. UI creates milestones and changes status or
deletes; it does not edit dependency graph/name/date after creation. Dashboard
counts future milestones in Not Started/In Progress states.

7. Folders — IMPLEMENTED, shallow organization
Frontend `Collections.tsx`; API GET/POST/PATCH/DELETE `/folders`; model Folder.
Create, rename, choose parent, delete. API checks parent existence, prevents
parent cycles, and prevents deleting non-empty folders or folders containing
projects. UI lists all entries flat; no nested tree/move UI, no moving projects.

8. Categories and 9. Technologies — IMPLEMENTED, basic catalogs
Frontend `CatalogPage` in `Collections.tsx`; GET/POST endpoints; Category and
Technology models. Add/list only. No edit/delete, color management or
technology-stack/project relation workflow from the UI.

10–17. Business/operations modules — PARTIAL GENERIC RECORD WORKFLOWS
Frontend: `RecordPage.tsx` and field maps; API `/records/:module` GET/POST,
PATCH/DELETE; model `WorkspaceRecord` stores module, title and Mixed fields.
Modules exposed by nav: clients, leads, services, proposals, invoices, finance,
security, technical-debt, testing, deployments, infrastructure, notifications.
The API also accepts documents/backups as generic record modules. Each has
module-specific allowlisted field names. The UI has generic list/create/edit/
delete forms. There are no dedicated Client, Lead, Invoice, Finance,
SecurityFinding, TestRun, DebtItem or Deployment models; relationships and
business rules are not relationally enforced. Numeric-looking form values are
submitted as strings by the generic input form; schema accepts string, number,
boolean, or null. No invoicing, payment processing, security scanning, test
execution, deployment trigger, or debt calculation is implemented.
Project-specific filtering uses `fields.project` string equality.
Finance records are separate from project financial totals on dashboard.

18. Documents and versions — PARTIAL / local filesystem storage
Frontend `Documents.tsx`; API `/documents`, `/documents/upload`, download,
replace, versions download, delete. Model `StoredDocument` with embedded
version array. Allowed extension/MIME pairs: PDF, TXT, MD, PNG, JPG/JPEG;
Multer limit 10 MiB and one file, UUID storage name. Upload records optional
project. Replacement embeds previous metadata/path; list hides storage names.
Downloads and deletion require admin session. Only local `server/uploads`
filesystem is used. Header MIME/extension checks do not inspect binary file
content; uploaded file data may be lost on ephemeral hosting replacement.
Backups/metadata export exclude bytes and document model records. No malware
scanning, cloud object store, checksum, retention, or quota is present.

19. Import/export — PARTIAL, additive metadata only
Frontend `ExportImportPage`; API GET `/export`, POST `/import`.
Exports projects, folders, catalogues, tasks, milestones, and workspace records.
Import schema limits each collection size; format must equal
`kenoratech-metadata-v1`. Existing `_id`s are skipped and rows failing insert
are counted as skipped. Imports omit users, sessions, activity, documents,
backups, and uploaded content. Import is non-transactional and can partially
complete. The import sanitizer drops unknown schema keys before create.

20. Backup/restore — PARTIAL, additive Mongo metadata snapshot
Frontend `BackupsPage`; API GET/POST `/backups`, GET `/backups/:id`, POST
`/backups/:id/restore`; model Backup. Snapshot includes the same seven metadata
collections as export; restore requires literal `RESTORE BACKUP` and adds rows
while skipping duplicate IDs/invalid rows. It does not replace/delete current
data, include files, users, sessions, activity or backup rows. No scheduled
backup, automatic retention, offsite copy, encryption-at-rest layer specific
to this app, or restore transaction exists. MongoDB provider backups need to
be configured independently.

21. Activity logs — PARTIAL audit trail
Frontend ActivityPage and dashboard list; API GET `/activity`; ActivityLog.
Project creation/edit/archive/duplicate and document upload/replace create
some records. It is not a comprehensive audit log: task/milestone/record and
catalogue changes do not all log. Filter by project uses `entityId`, which is
only a project ID for direct project events; related entities log their own
record ID or may lack a log, so it is not a reliable joined project audit.
API returns newest 100; dashboard newest eight.

22–25. GitHub, Vercel, Render — PARTIAL, implementation not
verified against live account credentials
Backend `providerActivity.ts`; GET `/provider-activity` and optional project
ObjectId query. Provider secret values are read from server environment and are
not sent to client. Project settings store repository URLs, live URLs, domains
and explicit Vercel project, Render service, provider resource IDs.
Recent events are fetched on request, sorted and capped at 250. Activity page
refresh interval is two minutes; project detail GitHub/deployments tab also
queries on open. No event cache/persistence, webhook, OAuth flow, background
sync, realtime feed, or provider-specific retry/backoff exists.
- GitHub: GitHub REST requests for recent issues (including PR entries in the
  issues response) and commits for linked repository URLs. It does not fetch
  issue/PR comments or full conversation messages. Two calls per repo run via
  `Promise.allSettled`; an individual rejection can be silently omitted.
- Vercel: lists up to 100 projects, matches explicit configured ID/name or
  exact app project name/slug, lists up to 10 deployments each, then attempts
  deployment events/log lines. Team ID is optional. Per-deployment event-log
  failures are swallowed; no complete or live log stream is guaranteed.
- Render: lists up to 100 services, matches ID/name/repository, lists up to 10
  deploys and attempts one-hour build log retrieval when owner ID is returned.
  Log API errors are swallowed. Logs may require supported service, plan and
  permissions.
- Removed provider: no longer queried
  history logs; also attempts Workers script/deployment listing. Pages and
  Worker endpoints require appropriate token permissions. Worker-list failure
  is tolerated so Pages events can still be returned.
- Each provider has a 12-second per-fetch timeout; there is no overall request
  deadline, aggregate concurrency cap, cache or explicit rate-limit handling.
  Failures at provider level return an error field and empty provider events;
  partial errors in some subrequests are intentionally suppressed.
These feeds are code-implemented but not live-account verified. “Configured”
means environment variable presence, not a successful authorization check.

26. Settings — PARTIAL
SettingsPage and IntegrationsPage query `/settings` and show environment
configuration flags. They do not edit secrets or perform provider authorization.
Provider events appear on Activity Logs and project tabs, not on the settings
page. Gemini flag is configuration presence only.

27. Search/filter — PARTIAL
Project list supports server-side text search (Mongo text index) and status,
plus pagination. Top-bar search state is passed to project/record pages; it is
not a global cross-collection search API. Document list supports optional name
query at backend, but current document page does not visibly expose a query
input. Task and milestone lists have no search/filter UI.

28. Notifications — PLACEHOLDER/GENERIC DATA
Notifications appears as a generic record module. No scheduling, email,
browser push, unread counter calculation, or notification delivery exists.
The bell icon has a static indicator rather than live unread state.

29. AI — NOT IMPLEMENTED
AI Assistant route renders IntegrationsPage and reports whether GEMINI_API_KEY
is present. No Gemini API request, prompt workflow, AI service or result storage
exists. `NotImplementedPage` exists but App does not route the AI page to it.

Additional module: Infrastructure uses the generic record page. It records
manual metadata only; it does not inspect cloud infrastructure.

State and data: TanStack Query cache/provider at main.tsx; each page uses

Forms/validation: native browser required/type/length constraints for many

Loading/error/empty: most major data pages implement query loading/error/empty
states. Provider Settings page indicates configuration only; project feed may
render an empty list without a tailored “no events” hint. Analytics handles
loading and aggregate errors. No global error boundary was found.

Responsive/theme: CSS contains mobile breakpoints, collapsible sidebar and
light/dark variable sets. Browser localStorage theme preference is applied to
document root.

Accessibility observations:

SECTION 5 — BACKEND AND API AUDIT
---------------------------------
Initialization (`server/src/server.ts`): dotenv is loaded; MONGODB_URI and a
SESSION_SECRET of at least 32 characters are required; DB connect occurs before
listen; PORT defaults to 4000. Database connect logs success.

Middleware order (`server/src/app.ts`): trust proxy in production, Helmet,
credentialed CORS for a single CLIENT_URL, 1 MiB JSON parser, Morgan tiny
request log, express-session with connect-mongo when MONGODB_URI is set,
login rate limiter, API router, 404, centralized error handler. Login limiter
is 10 requests per 15 minutes with standard headers. API session cookie:
kenora.sid, HttpOnly, SameSite=Lax, 12-hour max age, Secure only in production.

Common API behavior: version prefix `/api/v1`; JSON success generally
`{data: ...}`, errors `{error:{message}}`, lists may have `{meta}`. All routes
after `/auth/me` middleware require a valid database-backed session. Unsafe
methods POST/PUT/PATCH/DELETE require request Origin exactly equal to
CLIENT_URL (or localhost default). All authenticated accounts use the same
requireAuth middleware; no role-specific route middleware exists.

Endpoint inventory (all paths below are relative to `/api/v1`):

Public/auth:
- GET `/health` — no body; returns `{data:{status:"ok"}}`; no DB operation.
- POST `/auth/login` — body `{email,password}`; Zod email/password bounds;
  looks up User by lowercase email and bcrypt-compares; returns 401 for either
  unknown user or wrong password; regenerates session, saves lastLogin, returns
  email/name. Login throttled in app middleware.
- POST `/auth/logout` — destroys session, clears cookie, success object.
- GET `/auth/me` — session required; returns email/name; 401 when missing or
  invalid session.

Dashboard/integrations:
- GET `/dashboard` — auth required; no query/body. Aggregates project status,
  project financial fields, health, risk; counts milestones/tasks/archive;
  returns metrics, status rows, recent projects, activity, configured flags.
- GET `/provider-activity[?project=<ObjectId>]` — auth required; fetches saved
  project links and upstream provider data. Invalid ID returns 400. Returns
  events/providers configuration/error fields. Upstream/provider failures are
  represented per provider except some ignored subrequest failures.
- GET `/settings` — auth required; returns boolean credential-presence flags.

Projects:
- GET `/projects?page=&limit=&status=&q=` — auth; page >=1, limit 1–100,
  status exact, q Mongo text search; returns rows plus page/limit/total/pages.
- POST `/projects` — auth + matching Origin; project fields validated by
  `projectInput` (name, description/status/priority/risk, tags, links, provider
  resource identifiers, numeric values); unique slug generated; writes
  Project and ActivityLog; 201 data.
- GET `/projects/:id` — auth; loads/populates category/folder; 404 if missing.
- PATCH `/projects/:id` — auth + Origin; partial projectInput; update with
  validators; 404 if missing; adds activity.
- POST `/projects/:id/archive` — auth + Origin; stores prior status and marks
  Archived; activity; 404 if missing.
- POST `/projects/:id/restore` — auth + Origin; restores prior status or
  Planning; 404 if missing.
- POST `/projects/:id/duplicate` — auth + Origin; optional name; copies source
  fields then resets selected dates, metrics and assessment fields; creates
  unique slug; adds activity; 404 if missing.
- DELETE `/projects/:id` — auth + Origin; rejects with 409 if Task, Milestone,
  or WorkspaceRecord `fields.project` links exist; deletes Project otherwise;
  documents and other loose references are not included in guard.

Folders/catalogues:
- GET `/folders` — list sorted by name.
- POST `/folders` — body name, optional nullable parent/kind/project; checks
  parent; creates Folder; 201.
- PATCH `/folders/:id` — name/parent; parent existence/cycle validation; 404
  missing.
- DELETE `/folders/:id` — rejects children/projects with 409; then delete.
- GET/POST `/categories` — list sorted / create body name; unique name.
- GET/POST `/technologies` — list sorted / create name and optional category.
  Create conflicts can map Mongo duplicate key to 409.

Tasks/milestones:
- GET `/tasks[?project=id]` — list latest 200, populate project name.
- POST `/tasks` — validated title/description/project/status/priority/dueDate/
  estimatedHours; creates Task; 201.
- PATCH `/tasks/:id` — optional title/status/priority/dueDate; 404 missing.
- DELETE `/tasks/:id` — deletes or 404.
- GET `/milestones[?project=id]` — sorted by due date, populate project.
- POST `/milestones` — required name/project, optional dueDate/description;
  creates milestone; 201.
- PATCH `/milestones/:id` — optional name/dueDate/status/description; 404.
- DELETE `/milestones/:id` — deletes or 404.

Documents:
- GET `/documents[?project=id&q=text]` — optional project/name filter; regex
  input escaped; omits storage names; populates project name.
- POST `/documents/upload` — multipart `file`, optional project/documentType;
  10 MiB cap and allowlist; stores random UUID file then Mongo metadata and
  activity. Invalid project removes newly uploaded file and returns 400.
- GET `/documents/:id/download` — auth; reads local file and sends attachment;
  404 missing metadata/file.
- POST `/documents/:id/replace` — multipart file; embeds old file metadata as
  version, updates current file; 404 missing doc and removes newly received
  file.
- GET `/documents/:id/versions/:versionId/download` — auth; finds embedded
  version/path; 404 missing doc/version/file.
- DELETE `/documents/:id` — deletes metadata and current/version files; 404 if
  missing. Filesystem deletion is synchronous after DB deletion.

Activity/generic records:
- GET `/activity[?project=id]` — latest 100; project filter is entityId match.
- GET `/records/:module[?project=id]` — module must be allowlisted; latest 500;
  optional `fields.project` filter.
- POST `/records/:module` — title and fields; field keys/types/length checked,
  per-module allowlist; create WorkspaceRecord and activity; 201.
- PATCH `/records/:module/:id` — optional title/fields, same module checks;
  update or 404.
- DELETE `/records/:module/:id` — delete or 404.

Import/export/backups:
- GET `/export` — exports seven metadata collections (projects, folders,
  categories, technologies, tasks, milestones, records) as format v1.
- POST `/import` — body format and bounded arrays for seven collections;
  format mismatch 400; additive insert, existing IDs/invalid rows counted as
  skipped; returns per-collection counts.
- GET `/backups` — list metadata only; snapshot excluded.
- POST `/backups` — reads seven metadata collections and writes Backup snapshot;
  returns id/name/kind/time; source files excluded.
- GET `/backups/:id` — returns snapshot or 404.
- POST `/backups/:id/restore` — requires exact confirmation string; additive
  import behavior; returns counts and mode or 404.

Validation/error behavior: Zod errors and Mongoose validation map to 400;
duplicate key 11000 maps to 409; not-found default 404; unexpected errors log
server-side and return generic 500 text. Multer errors return 400 in upload
wrapper. No OpenAPI schema or controller/service separation exists beyond
providerActivity.

SECTION 6 — DATABASE AUDIT
--------------------------
Mongoose models are declared in `server/src/models/index.ts`; all use timestamps
except ActivityLog, which separately enables timestamps. Default Mongoose
collection naming is used (pluralized model names); connect-mongo uses
collection `sessions`.

User (`users`): email required/lowercase/unique, name optional, passwordHash
required, role enum admin default admin, lastLogin date. Unique email constraint.
No role expansion or reset token schema.

Project (`projects`): required name (trim, max 100), unique required lowercase
slug, description default empty, category/folder ObjectId references, tags,
status enum Planning/In Development/Active/Completed/Paused/Archived default
Planning, priority enum Low/Medium/High/Critical default Medium, risk enum
Not Assessed/Critical/High/Medium/Low, projectType default Software, stack
arrays, hosting providers, repo/live/domain links, provider identifiers,
dates, progress/health 0–100, budget/expense/revenue nonnegative numbers,
currency default INR, quality enums and notes/changelog/archive fields.
Indexes: unique slug; status+updatedAt; text name/description/tags.
References to Category and Folder are optional; other links are mostly loose.

Folder (`folders`): required trimmed max-100 name, nullable parent Folder ref,
kind folder/resource default folder, optional Project ref. Compound unique
parent+name index (Mongo null parent uniqueness means same-name root folders
may conflict). Timestamps.

Task (`tasks`): title required max 200; description default empty; optional
Project and Milestone refs; status enum Backlog/To Do/In Progress/In Review/
Blocked/Done default To Do; priority enum default Medium; dueDate, estimated/
actual hours, tags. Index project+status. Task.project is not required.

Milestone (`milestones`): required name max 200 and Project reference; optional
description/dueDate; status enum Not Started/In Progress/Completed/Delayed;
dependencies array of Milestone refs. Index project+dueDate.

ActivityLog (`activitylogs`): required action and description; optional
entityType/entityId; timestamps.

Category (`categories`): required unique name, optional color; timestamps.
Technology (`technologies`): required unique name and optional category string;
timestamps.

WorkspaceRecord (`workspacerecords`): required indexed module, required
trimmed title max 200, Mixed fields default empty object; compound module+
updatedAt and module+title text indexes. Application-level allowlists provide
field validation. References inside fields are strings, not Mongoose refs.

Backup (`backups`): required name, kind enum metadata default metadata,
required Mixed snapshot; timestamps.

StoredDocument (`storeddocuments`): required name max255, optional Project ref,
documentType default Other, required unique storageName, mimeType, size,
embedded versions holding name/storageName/mimeType/size/createdAt. Index
project+updatedAt. File bytes remain outside MongoDB.

Relationships/integrity:
- Project references category/folder; folder may refer project and parent.
- Task optionally references project/milestone; milestone requires project and
  can reference dependent milestones.
- StoredDocument optionally references project.
- Generic records can name project/client/etc. only inside untyped Mixed fields.
- No explicit Client, Invoice, Payment, Integration, Notification or
  Deployment models exist.
- No cascade deletes. Project deletion guards only tasks, milestones and
  generic records. Deleting task/milestone does not update any parent data.
- MongoDB transactions are not used. Multi-write operations (document write,
  activity write; import batches; restore) can leave partial results.
- Unique indexes are declared in schemas; no explicit migration/index rollout
  process is present. Production index availability was not inspected.

Dashboard calculations: project status aggregation excludes archived records;
separately counts archived and critical risk. Average health score uses
non-null numeric project values. Financial sums add `estimatedBudget`,
`actualExpenses`, and `recordedRevenue` on non-archived projects. Finance
WorkspaceRecords are not included. Upcoming count is milestones due in future
with active statuses; overdue count is tasks due before now and not Done.
These are sums of manually entered fields, not transaction-ledger accounting.

SECTION 7 — AUTHENTICATION AND SECURITY AUDIT
---------------------------------------------
High:
- Local file uploads are stored on the API filesystem, which is ephemeral in
  common Render deployments unless persistent disk is configured. Business
  impact: documents and versions can disappear independently of Mongo metadata.
  Evidence: `server/src/routes/api.ts` writes to `process.cwd()/uploads`;
  `docs/deployment.md` acknowledges persistence limitation. Recommendation:
  use managed object storage or an explicitly configured persistent volume,
  add reconciliation/backup and retention policy.

Medium:
- File type validation trusts extension and request MIME; file contents are
  not signature-inspected or malware-scanned. Risk: spoofed files may be stored
  and downloaded. Affected `api.ts` Multer filter. Add content sniffing,
  malware scanning, and stricter safe-download policy.
- Session cookie is SameSite=Lax and CSRF protection for unsafe methods is
  exact Origin match. This is meaningful browser-origin protection, but there
  is no CSRF token; test reverse proxy/production origin behavior and consider
  token-based defense if supporting non-browser clients. CORS allows one
  configured origin with credentials.
- Login limiter is memory-backed default express-rate-limit. Multi-instance
  deployments do not share counters; use a shared store where horizontal scale
  matters.
- `requireAuth` verifies session user existence but not `role`. Current User
  enum restricts records to admin, so present impact is limited; add explicit
  authorization before introducing roles.
- Session secret fallback exists inside `app.ts` for direct app construction,
  but `server.ts` prevents normal startup without a 32-character configured
  value. Tests set their own secret. Ensure production always uses unique
  secret and protect rotation.
- Provider calls have no server cache or rate limiter. Authenticated requests
  can trigger many external requests per project and consume quotas or slow
  responses; provider requests have per-fetch timeout only.
- Project deletion does not check documents, risking orphan document metadata
  and storage files. Loose references add integrity risk.

Low / informational:
- bcrypt hash work factor is 12; no password policy beyond seeded admin
  minimum 12-character length. Login accepts passwords up to 200 characters.
- Helmet is installed and applied; React renders text normally (no
  dangerouslySetInnerHTML usage found in source search). No CSP customization
  or penetration test was inspected.
- Zod bounds JSON input to 1 MiB and validates route body shapes. NoSQL query
  values are generally string/enum-converted; document regex query escapes
  regex metacharacters.
- Provider tokens are environment variables, not stored in database and not
  returned to client. There is no token encryption-at-rest feature in the app;
  host secret manager and environment access controls are relied on.
- API logs via Morgan tiny include method/path/status/latency; no request ID,
  structured audit logger, secret redaction audit or log retention policy is
  configured here.
- Admin account creation is not open registration. Seed uses bcrypt and
  `$setOnInsert`; it deliberately does not overwrite existing credentials.
- Download endpoints are authenticated and use `res.download`; generated UUID
  names plus `basename` reduce path traversal exposure. File upload data remains
  local. Browser-authenticated admin is the only authorization level.

  0.0.0.0/0 except temporary deliberate setup. Ensure index creation and
  automated Atlas backup plan.

  blocks unsafe API calls.

SECTION 13 — PRIORITIZED ISSUES AND RECOMMENDATIONS
---------------------------------------------------
1. High — Durable document storage. Evidence: uploadDir is local cwd/uploads;
   metadata backup/export exclude file bytes. Business impact: file loss on
   instance replacement. Recommendation: managed object storage or persistent
   disk, retention/reconciliation and backup; dependency: provider bucket and
   access policy.
2. High — Provider feed reliability/quotas. Evidence: fan-out per feed request,
   no cache/retry/backoff/pagination; some subcall failures silently omitted;
   12-sec timeout per request, not whole operation. Impact: slow feeds, rate
   limits, incomplete event history. Add bounded concurrency, short cache,
   provider-specific error detail, retry for transient 429/5xx and pagination;
   dependencies: API quota and desired freshness.
3. High — Database/object relationship integrity. Evidence: generic Mixed
   references and incomplete project-delete guard; no transaction/cascades.
   Impact: orphaned files and records. Add normalized references and deletion
   policy/reconciliation. Dependency: data migration design.
4. High — Backup scope and recoverability. Evidence: only seven collections;
   no file bytes, users/activity. Impact: snapshots cannot fully restore the
   workspace. Expand backup format and maintain provider-side independent
   backup. Dependency: storage strategy and retention.
5. Medium — Authentication lifecycle. Evidence: no reset/change password or
   MFA; existing seed user never updated. Impact: credential recovery/rotation
   is operationally awkward. Add audited reset flow and documented admin
   rotation; ensure single admin semantics deliberate.
6. Medium — CSRF/session deployment verification. Evidence: same-site cookie
   across separate default host domains and exact Origin check. Impact:
   browser cookie blocking or write requests rejected in production. Use shared
   parent custom domain and production browser tests; consider CSRF token.
7. Medium — Request-size, login and API scaling. JSON bounded and login
   throttled, but limiter is process-local and provider route can cause external
   fan-out. Use distributed limit/cache when scaling.
8. Medium — Financial accuracy. Evidence: dashboard totals only sum fields on
   Project, while Finance has separate generic records. Impact: users may read
   project totals as full ledger. Define one accounting source and reconcile.
9. Medium — Activity audit completeness. Evidence: not all mutations write
   activity and project filter is entityId-only. Add centralized audit helper,
   actor/time/object/project refs and audit coverage tests.
10. Medium — Vercel SPA route fallback. Evidence: BrowserRouter nested paths;
    no rewrite config found. Test production deep-link refresh and configure
    fallback to index.html as needed.
11. Medium — Generic modules lack domain rules. Evidence: free-form Workspace-
    Record with module allowlist but no Client/Invoice/etc entities. Impact:
    weak relationships, finance and workflow validation. Create domain models
    only after defining user workflows and migration path.
12. Low — Accessible interaction states. Add dialog/focus/keyboard support,
    explicit accessible names, and run accessibility checks.
13. Low — Maintainability. Break up long one-line Express routes and giant
    feature components, remove confirmed unused dependencies/duplicate page
    implementation, add lint/format conventions.
14. Low — Search/pagination completeness. Add global search endpoint or rename
    current search; consume pagination metadata and expose document search.
15. Low — Docs synchronization. `docs/database-schema.md` says document,
    backup and business models are future work, while current code has
    StoredDocument, Backup and generic WorkspaceRecord. `docs/integrations.md`
    is newer than some setup/architecture docs; retain a single source of truth.
